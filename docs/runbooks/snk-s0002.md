# Runbook — `SNK-S0002`, archive conflict

**Class:** fatal. Queries on the affected table are refused until a human acts.

## Symptom

Every query touching one table is refused with `SNK-S0002`. Other tables are unaffected.

## What is actually wrong

The archival registry says a range was purged from the live tier and is now held only in the
archive. The live catalogue says rows in that range are present. Both cannot be true, and the
system cannot tell which one is right — so it refuses rather than choosing.

The usual cause is **a restore that resurrected purged rows.** The transactional store was
restored from a backup taken before a purge, the purged range came back with it, and capture
published it again. Nothing in that sequence is detectably wrong at the time it happens; it
only becomes visible when the registry and the catalogue are next compared.

Refusing is deliberate. Answering from the live tier would return rows the archive
authoritatively says were removed; answering from the archive would omit rows that are
demonstrably present. Either answer is wrong and neither is marked as such.

## What to do

**Decide which copy is authoritative.** This is a judgement about the data, not about the
system, and it is why this error waits for a person.

- **The archive is right** — the restore was a mistake and those rows should be gone.
  Re-purge the range. The purge path verifies before it removes, so it will refuse if the
  live rows and the archived rows do not match, which is itself the answer to whether the
  restore was clean.
- **The live tier is right** — the purge was premature and the data is wanted back.
  Re-adopt the range: the registry is updated to say the range is live, and the archived copy
  becomes redundant rather than authoritative.

**Do not** clear the registry entry to make the error stop. That removes the disagreement
without resolving it, and the next reconciliation will not find it because there will be
nothing left to disagree with.

## What "fixed" looks like

Queries on the table succeed, and a reconciliation of that table against the source is clean.
Run the reconciliation explicitly — an error that stops appearing is not the same as a
conflict that was resolved.
