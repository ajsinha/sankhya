# Runbook — `SNK-S0003`, archive verification failed

**Class:** fatal. **Terminal until a human acts. There is no automatic retry.**

## Symptom

An archive verification run reports `SNK-S0003`. If this fired during a purge, the purge
stopped and nothing was removed.

## What is actually wrong

Before anything is purged from the live tier, the archived copy is verified against it: the
data is read back, canonically encoded, and digested, and the digests must match exactly.
This error means they did not.

**There is no retry, and that is the design.** A mismatch means a defect exists — in the
encoder, in the archive's storage, in the read path, or in the verification itself. Retrying
would run the same defect again. The only outcomes of a retry are the same failure, which
wastes time, or an intermittent pass, which is far worse: it would let a purge proceed
against a copy that is wrong in a way that comes and goes.

## What to do

**Nothing is lost yet.** The purge did not proceed. The live tier still holds the data. There
is no time pressure and there is no partial state to clean up — this is the whole reason
verification happens before removal rather than after.

**Capture a diagnostic bundle before anything else.** The evidence is in the current state
and re-running things destroys it.

**Then narrow it to one of three:**

1. **The archived bytes are wrong.** Re-archiving the range and re-verifying will pass. If it
   does, the fault was in the write and the archive's storage is suspect.
2. **The archived bytes are right and the encoding is not deterministic.** Verify the same
   range twice without re-archiving. Two different digests from the same unchanged data means
   the canonical encoding is not canonical, which is a defect in this system and affects
   every archived range rather than this one.
3. **The live copy changed after archival.** Compare the live range's current digest against
   what was recorded at archival time. A live tier that changed underneath a completed
   archival means something wrote to a range that was supposed to be frozen.

**Do not purge the range by hand to unblock the pipeline.** Purging past a failed
verification is the single action this system is most carefully arranged to prevent, and
doing it manually removes the system of record before the copy is known to be good.

## What "fixed" looks like

A verification run passes on the affected range, *and* the cause was identified. A
verification that passes on the second attempt with no explanation is case 2 above until
proven otherwise.
