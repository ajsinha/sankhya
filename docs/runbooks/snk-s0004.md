# Runbook — `SNK-S0004`, source endangered

**Class:** fatal. **The analytical tier is being sacrificed to protect the transactional
store. This is the system working.**

## Symptom

`SNK-S0004` is reported, capture for one or more tables stops, and a gap marker is recorded.
A re-snapshot begins automatically. Analytical queries for recent data start being refused
with `SNK-S0001` until the re-snapshot completes.

## What is actually wrong

Nothing, in the sense that matters. Something is wrong upstream and this is the response.

A logical replication slot holds write-ahead log on the transactional store until the
consumer has processed it. If the consumer falls behind and stays behind, the retained log
grows without bound — and when it fills the volume, **the transactional database stops
accepting writes.** The analytical tier's slowness would have taken down the system of
record.

The escalation ladder exists to make sure that cannot happen. Retained log is watched, the
commit interval is lengthened first, backpressure is applied, and if the retained volume
still reaches its limit, capture drops the slot. Losing the analytical copy's continuity is
recoverable by re-snapshotting. A transactional store that cannot accept writes is an outage
of the business.

**An analytical component must never be able to take down the transactional one.** That is a
release gate for this system, and this error is what it looks like when it holds.

## What to do

**Confirm the transactional store is healthy first**, before looking at anything analytical.
That is what was being protected; check it was.

**Then find out why publication fell behind.** The ladder fired because the consumer could
not keep up for long enough to matter. Common causes, in the order worth checking:

- **Publication throughput is the bottleneck.** Compaction competing with the applier is the
  usual reason — check the maintenance duty cycle. The applier never yields; maintenance
  yields to it, so a duty cycle set too high starves publication rather than the reverse.
- **Storage got slower.** Publication writes Parquet. If object storage degraded, publication
  degrades with it and the slot backs up behind it.
- **The write rate genuinely rose** and the configuration has not kept up. This is capacity,
  not a fault.

**Let the re-snapshot run.** It is automatic and it is the correct repair: the gap marker
records that continuity was lost, and the snapshot re-establishes it from a consistent point.
Stopping it leaves the gap permanently.

## What "fixed" looks like

The re-snapshot completes, the gap marker is resolved, and reconciliation of the affected
tables against the source is clean. Retained log volume falls back to its ordinary range and
stays there under the same load that caused this — otherwise the cause was not addressed and
the ladder will fire again.

## What not to do

**Do not raise the retained-log limit to stop this recurring.** The limit is the point at
which the analytical tier is sacrificed instead of the transactional one. Raising it moves
that point closer to a database that cannot accept writes.
