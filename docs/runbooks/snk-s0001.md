# Runbook — `SNK-S0001`, coverage gap

**Class:** fatal. **This is a correctness event, not a performance one.**

## Symptom

A query is refused with `SNK-S0001`. Other queries against the same table may succeed —
whether one is refused depends on the range it asks for, so the failure looks intermittent
and looks like a bug in the client.

## What is actually wrong

A read is answered from tiers — the arrival buffer, published Parquet, and in future the
archive — and the planner splices them into a cover of the requested position range. This
error means **no tier covers part of that range**: there is a hole between where one tier
ends and the next begins.

The query was refused rather than answered from the tiers that *do* cover their parts. That
choice is the whole point of the error. A partial answer here would be a smaller number
returned as though it were the complete one — no row is marked missing, nothing is null,
and the result is simply short. Nobody notices a sum that is 3% low.

A gap arises when something removed data a reader still needs. In practice:

- **Retention removed published files** that the requested range needs, because retention is
  shorter than the range queries actually ask for.
- **Capture had a discontinuity** and a gap marker was recorded — see `SNK-S0004`, which is
  the alert that fires when that happens deliberately.
- **A restore** put the transactional store back to a point behind what was already
  published, so positions were reused.

## What to do

**First, establish which of the three it is.** The detail on the error names the uncovered
range. Compare it against:

```bash
sankhya-server doctor
```

and the table's own log. A gap at the *old* end of the range is retention. A gap in the
*middle* is a capture discontinuity. A gap where two tiers claim the same positions is a
restore.

**Do not retry.** There is no automatic retry for this error and adding one would convert a
detectable fault into a query that eventually returns a wrong answer when a tier moves.

**If it is retention:** lengthen it, and accept that the already-removed range cannot be
recovered from this system. Queries for it will keep being refused, which is correct.

**If it is a capture discontinuity:** a re-snapshot of the affected table is the repair. The
gap marker exists so that this is a decision somebody makes rather than something that
resolves itself into a wrong answer.

**If it is a restore:** stop capture before doing anything else. A restore that resurrects
positions already published produces two different sets of data claiming the same positions,
and every further commit makes the reconciliation harder.

## What "fixed" looks like

The refused query succeeds. Not "stops erroring" — *succeeds*, and its result reconciles
against the source. A coverage gap that stops being reported without the range being restored
means a tier's coverage claim changed, not that the data came back.
